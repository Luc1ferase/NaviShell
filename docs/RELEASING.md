# Releasing NaviShell (maintainers)

This is the maintainer-side procedure. End users only need the
[Releases page](https://github.com/Luc1ferase/NaviShell/releases); plugin authors only need
the README.

## Continuous integration

Every push to `master` and every pull request runs `.github/workflows/ci.yml`:

- **Frontend**: `pnpm typecheck`, `pnpm lint`, `pnpm build` (plugin bundles + `dist/`).
- **Rust** on Ubuntu, Windows and macOS: `cargo fmt --check`, `cargo clippy -D warnings`,
  `cargo check`. `pnpm build` runs first because `tauri::generate_context!()` needs `dist/`.

Nothing is packaged in CI; installers only come from the release workflow below.

## Cutting a release

1. Bump the version in all three places: `package.json`, `src-tauri/tauri.conf.json` and
   `src-tauri/Cargo.toml`. Open a PR, let CI pass, merge.
2. Tag the merge commit on `master` and push the tag (or dispatch the workflow by hand with
   `gh workflow run release.yml --ref master`):

   ```bash
   git tag v0.3.0 && git push origin v0.3.0
   ```

3. `.github/workflows/release.yml` builds on Windows x64, macOS (Intel + Apple Silicon) and
   Linux x64 + arm64, and uploads the installers, each installer's `.sig` signature and the
   update manifest `latest.json` to one **draft** release.
4. Review the assets, then publish. **The release must really be published (not left as a
   draft, not flagged as a pre-release)**, otherwise the updater never sees it: clients read
   `releases/latest/download/latest.json`, and GitHub's `latest` only points at published,
   non-pre-release releases.

   Until it is published, a draft has no tag: its URL is `releases/tag/untagged-<hash>`
   (`gh release view v0.3.0 --json url` prints it) and `releases/tag/v0.3.0` is a 404.
   Publishing a draft that came from a manual dispatch creates the tag at that moment; the
   workflow's `guard` job notices that the tag already has a published release and skips
   the build the tag push would otherwise start, so no duplicate draft appears.

## Update signing

Signing updates needs two repository secrets; the build fails if either is missing:

| Secret                               | Content                                                             |
| ------------------------------------ | ------------------------------------------------------------------- |
| `TAURI_SIGNING_PRIVATE_KEY`          | the minisign private key generated by `pnpm tauri signer generate` |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | the password chosen when generating it                              |

Set them with `gh secret set <NAME> < file` or in the repository settings. The public half is
`plugins.updater.pubkey` in `src-tauri/tauri.conf.json`.

**Rotating the key pair abandons every installed build**: old clients only trust the public
key compiled into them and would have to be reinstalled by hand, so keep the private key
backed up outside the repository.

## Plugin releases

Plugins that live in `packages/` but are not bundled with the app (they are absent from
`public/builtin-plugins.json`; today `packages/plugin-hwmon`) reach users through the
marketplace index `registry/plugins.json`, so they have their own, lighter flow:

1. On a branch, bump `version` in the package's `plugin/plugin.json` (and `package.json`)
   and add the version to the package's `CHANGELOG.md`. Push the branch.
2. Build and pack locally to learn the digest:

   ```bash
   pnpm --filter ./packages/plugin-hwmon build
   node scripts/pack-plugin.mjs packages/plugin-hwmon   # prints zip=…, sha256=…
   ```

   The zip is deterministic (stored entries, fixed timestamps), so this digest is the one
   the workflow will produce for the same sources.
3. Dispatch **Plugin release** from that branch
   (`gh workflow run plugin-release.yml --ref <branch> -f package=plugin-hwmon`). It
   builds, packs, and creates the release `plugin-<id>-v<version>` with the zip and a
   `.sha256` file attached. The release is a **pre-release** so that `releases/latest`,
   which the app updater reads, keeps pointing at the newest app release. The `sha256` in
   the job summary must equal the one from step 2; if it does not, the sources differ
   from what was pushed.
4. Update the entry in `registry/plugins.json` on the same branch: move the current
   `version` / `url` / `sha256` / `minHostVersion` to the top of `releases` (with the
   release `date`), then set the new `version`, `url`
   (`https://github.com/Luc1ferase/NaviShell/releases/download/plugin-<id>-v<version>/<id>-<version>.zip`)
   and `sha256`, and run `pnpm exec prettier --write registry` and
   `node scripts/check-registry.mjs`. Open the PR: the **Registry** workflow downloads the
   published asset and checks its digest and manifest against the entry, so a mismatch
   blocks the merge rather than a user's install.
5. Merge. If the plugin sources change during review, run step 3 again (the workflow
   replaces the assets of an existing release) and update the digest in the entry.

The app verifies the digest before unpacking, so even a wrong entry fails safely: the
install is refused, nothing half-installed is left behind.

## Forks

A fork that wants its own release channel must:

- generate its own key pair and set the two secrets above in the fork;
- replace `plugins.updater.pubkey` and the `endpoints` URL in `src-tauri/tauri.conf.json`;
- keep `bundle.createUpdaterArtifacts` enabled so `.sig` files and `latest.json` are produced.
