# Releasing NaviShell (maintainers)

This is the maintainer-side procedure. End users only need the
[Releases page](https://github.com/Luc1ferase/NaviShell/releases); plugin authors only need
the README.

## Continuous integration

Every push to `master` and every pull request runs `.github/workflows/ci.yml`:

- **Frontend**: `pnpm typecheck`, `pnpm lint`, `pnpm build` (plugin bundles + `dist/`).
- **Rust** on Ubuntu, Windows and macOS: `cargo fmt --check`, `cargo clippy -D warnings`,
  `cargo check`. `pnpm build` runs first because `tauri::generate_context!()` needs `dist/`.

Nothing is packaged in CI; installers only come from the release workflow below.

## Cutting a release

1. Bump the version in all three places: `package.json`, `src-tauri/tauri.conf.json` and
   `src-tauri/Cargo.toml`. Open a PR, let CI pass, merge.
2. Tag the merge commit on `master` and push the tag (or dispatch the workflow by hand with
   `gh workflow run release.yml --ref master`):

   ```bash
   git tag v0.3.0 && git push origin v0.3.0
   ```

3. `.github/workflows/release.yml` builds on Windows x64, macOS (Intel + Apple Silicon) and
   Linux x64 + arm64, and uploads the installers, each installer's `.sig` signature and the
   update manifest `latest.json` to one **draft** release.
4. Review the assets, then publish. **The release must really be published (not left as a
   draft, not flagged as a pre-release)**, otherwise the updater never sees it: clients read
   `releases/latest/download/latest.json`, and GitHub's `latest` only points at published,
   non-pre-release releases.

## Update signing

Signing updates needs two repository secrets; the build fails if either is missing:

| Secret                               | Content                                                             |
| ------------------------------------ | ------------------------------------------------------------------- |
| `TAURI_SIGNING_PRIVATE_KEY`          | the minisign private key generated by `pnpm tauri signer generate` |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | the password chosen when generating it                              |

Set them with `gh secret set <NAME> < file` or in the repository settings. The public half is
`plugins.updater.pubkey` in `src-tauri/tauri.conf.json`.

**Rotating the key pair abandons every installed build**: old clients only trust the public
key compiled into them and would have to be reinstalled by hand, so keep the private key
backed up outside the repository.

## Forks

A fork that wants its own release channel must:

- generate its own key pair and set the two secrets above in the fork;
- replace `plugins.updater.pubkey` and the `endpoints` URL in `src-tauri/tauri.conf.json`;
- keep `bundle.createUpdaterArtifacts` enabled so `.sig` files and `latest.json` are produced.
